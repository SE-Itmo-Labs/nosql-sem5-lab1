# Маршрут защиты лабораторной работы

## Подготовка

1. Запустить проект по инструкции из `DEVELOPMENT.md` с учебными данными.
2. Войти как `client01` и открыть афишу.
3. Во второй сессии подготовить того же клиента либо администратора для
   демонстрации конкуренции и лабораторного раздела.

## Клиентский сценарий

1. Выбрать фильм, сеанс и два свободных места.
2. Продолжить оформление. Ожидается удержание обоих мест и обратный отсчёт TTL.
3. Во второй сессии открыть тот же сеанс. Места имеют статус `HELD`, повторное
   пересекающееся удержание возвращает `409` целиком, без частичного результата.
4. Добавить товар кинобара и подтвердить заказ. Ожидаются заказ, два билета,
   снимки цен и статус мест `BOOKED`.
5. Открыть уведомления. Ожидаются системные сообщения об удержании и
   подтверждении; сообщение можно отметить прочитанным.
6. Отменить заказ раньше чем за 30 минут до сеанса. Ожидаются `CANCELLED`,
   освобождённые места и одно системное уведомление об отмене.

## Механизмы Redis

1. **TTL:** удержать место, не подтверждать заказ и дождаться обратного отсчёта.
   После истечения место снова `AVAILABLE`.
2. **Распределённая блокировка:** параллельно подтвердить конкурирующие заказы.
   Один запрос завершается успешно, второй получает предметный конфликт;
   уникальный индекс PostgreSQL остаётся окончательной защитой.
3. **Cache-aside:** администратором открыть категорию дважды. Первый источник —
   `DATABASE`, второй — `CACHE`; после изменения кэш инвалидируется.
4. **Атомарная запись:** создать уведомление и показать одновременно объект
   `notification:{id}` и ID в `notification:user:{username}`.
5. **Согласованность:** в лабораторном разделе выбрать реальный сеанс. Сравнить
   `EVENTUAL` с `WAIT_FOR_REPLICA`; затем отключить реплику, повторить чтение и
   подключить её обратно. Ключ имеет вид `laboratory:screening:{id}` и не
   участвует в бронировании.

## Архитектурные ответы

- PostgreSQL является источником истины для каталога, заказов и билетов.
- Redis хранит краткоживущие удержания, уведомления, кэш и координационные ключи.
- Redisson уменьшает число конфликтов, а частичный уникальный индекс исключает
  двойную продажу даже при сбое блокировки.
- PostgreSQL outbox сохраняет событие вместе с заказом; повторная доставка в
  Redis не создаёт дубликат благодаря ID события.
- `WAIT` уменьшает окно рассогласования, но не гарантирует синхронную запись на
  диск и не превращает репликацию Redis в строгую согласованность.
