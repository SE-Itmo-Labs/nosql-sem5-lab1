# Отчёт по лабораторной работе №1

## Постановка задачи

Вариант `1869847`: личный кабинет клиента кинотеатра. Основной объект —
уведомление, обязательный сценарий — отправка уведомлений. Основное NoSQL-хранилище
— Redis.

Дополнительные требования варианта:

- временная блокировка ресурса;
- кэширование справочника категорий;
- распределённая блокировка;
- исследование согласованности чтения и записи.

## Использованные технологии

- Java 25, Spring Boot 4.1.1 и Gradle;
- Redis 8.10.1: primary и две реплики;
- PostgreSQL 18.6;
- Redisson;
- SpringDoc OpenAPI;
- JUnit, Mockito и Testcontainers;
- Nuxt frontend.

## Обоснование Redis

Уведомление и категория естественно представляются парой «ключ → JSON». Redis
подходит для быстрого чтения объектов, атомарного счётчика, Sorted Set, TTL,
Lua-операций и распределённой блокировки. При этом пользователи и исходный
справочник категорий остаются в PostgreSQL, поскольку для них важны ограничения
схемы и постоянное хранение.

Полная схема ключей и структура кода приведены в
[архитектуре backend](BACKEND_ARCHITECTURE.md).

## Реализованные сценарии

### Отправка уведомлений

ID создаётся через `INCR`. JSON уведомления и ID в пользовательском Sorted Set
сохраняются одним Lua-скриптом. История клиента возвращается в обратном
хронологическом порядке.

### Временные данные

Бронь места создаётся через `SET IF ABSENT` с TTL. Вторая попытка получает
`409 Conflict`, а после истечения TTL Redis удаляет ключ без фоновой задачи
Spring.

### Кэширование

Для категорий используется cache-aside с TTL 5 минут. При первом запросе
источником ответа является `DATABASE`, при повторном — `CACHE`. Изменение данных
обновляет или инвалидирует связанные ключи.

### Распределённая блокировка

`Redisson RLock` защищает критическую секцию. В проверке с двумя параллельными
запросами первый получил `acquired: true`, второй — `acquired: false`. После
освобождения следующий запрос снова получил блокировку.

### Персистентность

Primary использует AOF `everysec` и RDB-снимки. Папка `/data` подключена к
`redis_data/` на хосте. Контрольный ключ сохранился после перезапуска primary,
после чего обе реплики восстановили соединение.

## Исследование согласованности

В эксперименте использовались primary и две асинхронные реплики.

1. В primary записано `version-1`. Все три ноды вернули одинаковое значение.
2. `replica-1` отключена от primary.
3. В primary записано `version-2` в режиме `ASYNC`.
4. Primary и `replica-2` вернули `version-2`, отключённая `replica-1` —
   `version-1`.
5. Два чтения в режиме `REPLICA_PREFERRED` показали сначала устаревшее, затем
   актуальное значение.
6. После обратного подключения `replica-1` получила актуальное состояние.
7. Запись с `WAIT_FOR_REPLICAS` получила `replicasAcked: 2`.

Таким образом, асинхронная репликация допускает чтение устаревшего значения.
`WAIT` позволяет дождаться заданного количества подтверждений и уменьшает это
окно ценой дополнительного ожидания. При этом подтверждение реплики не равно
сохранению на диск и не превращает Redis в строго согласованную систему.

Эндпоинт `/api/v1/consistency/experiments` возвращает `writeDurationMs`,
`waitDurationMs` и `readDurationMs`, поэтому измерения можно повторить на машине,
где проходит защита, без изменения кода.

## Проверка

- unit-тесты проверяют сервисы, авторизацию и обработку конфликтов;
- Testcontainers запускает изолированный Redis для интеграционных тестов;
- проверены реальные HTTP-сценарии cache miss/hit, TTL, параллельной блокировки,
  отключения и восстановления реплики;
- итоговый набор содержит 33 теста.

## Вывод

Redis хорошо подходит для уведомлений, краткоживущих броней, кэша и координации
нескольких обработчиков. Его команды позволяют реализовать атомарные операции
без сложного кода приложения. PostgreSQL при этом удобнее для постоянных данных
со строгой схемой.

При использовании реплик необходимо учитывать eventual consistency: чтение с
реплики может отставать от primary. Команда `WAIT` снижает вероятность такого
чтения, а AOF и RDB решают отдельную задачу восстановления после перезапуска.
