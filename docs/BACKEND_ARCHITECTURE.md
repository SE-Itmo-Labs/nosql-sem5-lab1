# Архитектура backend

Backend построен на Java 25 и Spring Boot 4.1.1. PostgreSQL хранит постоянные
пользовательские данные и справочник категорий, Redis отвечает за уведомления,
кэш, временные данные, блокировки и эксперимент с репликацией.

## Структура

```text
src/main/java/org/seitmolabs/
├── common/
│   ├── dto/                         # общие структуры запросов
│   └── exceptions/                  # единая обработка ошибок REST
├── config/
│   ├── DataInitializer.java         # тестовые пользователи и категории
│   ├── OpenApiConfig.java           # Swagger и заголовки входа
│   ├── RedissonConfig.java          # клиент распределённой блокировки
│   └── WebConfig.java               # CORS
└── modules/
    ├── auth/                         # демонстрационный вход без Spring Security
    ├── user/                         # пользователь и GET /users/me
    ├── notification/                 # основной объект, хранение в Redis
    ├── categories/                   # PostgreSQL + cache-aside в Redis
    ├── block/                        # TTL и распределённая блокировка
    └── consistency/                  # primary, две реплики и эксперименты
```

Каждый предметный модуль разделён на небольшие части:

- `controller` принимает HTTP-запрос и формирует ответ;
- `service` содержит последовательность действий сценария;
- `repository` работает с PostgreSQL или Redis;
- `domain` содержит модель;
- `dto` содержит внешние структуры запросов и ответов.

## Прохождение запроса

Защищённый запрос сначала проходит через `SimpleAuthFilter`. Фильтр читает
`X-Username` и `X-Password`, проверяет пользователя через PostgreSQL и кладёт
его в атрибут запроса. Контроллер получает текущего пользователя, вызывает
сервис, а сервис обращается к одному или нескольким репозиториям.

Spring Security и JWT намеренно не используются: для лабораторной оставлена
прозрачная схема, которую легко показать и объяснить. Пароли хранятся открыто
только в демонстрационной среде и не подходят для production.

## Распределение данных

| Данные | Хранилище | Представление |
| --- | --- | --- |
| Пользователи | PostgreSQL | таблица `app_users` |
| Категории | PostgreSQL | таблица `categories` |
| Кэш категории | Redis | `category:{id}` → JSON, TTL 5 минут |
| Кэш списка категорий | Redis | `category:all` → JSON, TTL 5 минут |
| Уведомление | Redis | `notification:{id}` → JSON |
| Индекс уведомлений клиента | Redis | `notification:user:{username}` → Sorted Set |
| Счётчик уведомлений | Redis | `notification:seq` → число |
| Временная бронь | Redis | `block:{resourceKey}` → JSON с TTL |
| Распределённая блокировка | Redis/Redisson | `lock:{resourceKey}` |
| Экспериментальные значения | Redis primary/replicas | `consistency:{key}` |

JSON выбран для объектов, потому что он сохраняет модель целиком и остаётся
читаемым через `redis-cli`. Sorted Set позволяет хранить ID уведомлений в
порядке времени создания без полного просмотра всех ключей.

## Уведомления

При создании уведомления Redis-команда `INCR` выдаёт новый ID. Затем Lua-скрипт
одной атомарной операцией:

1. сохраняет JSON по ключу `notification:{id}`;
2. добавляет ID в Sorted Set пользователя.

Это не позволяет получить уведомление без индекса или индекс без объекта.
Список читается от новых уведомлений к старым.

## Cache-aside для категорий

PostgreSQL является источником истины. Чтение категории выполняется так:

1. сервис проверяет `category:{id}` в Redis;
2. при cache hit сразу возвращает объект и оставшийся TTL;
3. при cache miss читает PostgreSQL и записывает результат в Redis на 5 минут.

Обновление категории сразу заменяет её кэш и удаляет `category:all`. Удаление
категории очищает обе кэшированные записи. Поэтому старое значение не остаётся
доступным после изменения источника.

## Два вида блокировок

Временная блокировка использует `SET IF ABSENT` с TTL. Повторный запрос не
перезаписывает владельца и время жизни. Redis автоматически удаляет истёкший
ключ. Досрочное освобождение сравнивает сохранённый JSON и удаляет ключ одним
Lua-скриптом.

Распределённая блокировка использует `Redisson RLock`. Метод `tryLock()`
разрешает войти только одному запросу, а `finally` освобождает блокировку даже
при исключении внутри критической секции. Эндпоинт `/locks/execute` удерживает
её заданное время, чтобы наглядно запустить два конкурирующих запроса.

## Репликация и согласованность

Docker Compose запускает primary Redis и две асинхронные реплики. Обычные
записи выполняются только в primary.

- `MASTER` читает актуальное значение из primary;
- `REPLICA_PREFERRED` по очереди читает реплики и при недоступности использует
  primary;
- `ASYNC` отвечает после записи в primary;
- `WAIT_FOR_REPLICAS` выполняет `WAIT` на том же соединении, что и запись.

Диагностические методы позволяют отключить реплику командой `REPLICAOF NO ONE`,
увидеть устаревшее значение и подключить её обратно. `WAIT` уменьшает окно
рассогласования, но не создаёт транзакцию между узлами и не гарантирует запись
на диск.

## Персистентность

Primary сохраняет данные в подключённой папке `redis_data/`:

- AOF включён с `appendfsync everysec`;
- RDB-снимки создаются по расписанию;
- AOF автоматически переписывается и использует RDB-преамбулу;
- после перезапуска primary загружает сохранённые данные, а реплики повторно
  синхронизируются с ним.

## Ошибки и Swagger

`GlobalExceptionHandler` преобразует исключения в единый JSON-ответ со статусом,
сообщением и путём запроса. Основные статусы: `400`, `401`, `404`, `409`, `500`.

SpringDoc строит OpenAPI из реальных контроллеров. Swagger UI содержит два
глобальных API-key поля: `X-Username` и `X-Password`. Метод входа и сама
документация доступны без этих заголовков.

## Тестирование

Unit-тесты изолированно проверяют сервисы и HTTP-фильтр. Интеграционный набор
через Testcontainers поднимает отдельный Redis и проверяет реальные команды:

- атомарное сохранение уведомления и индекса;
- истечение TTL-блокировки;
- кэш категории и списка;
- конкуренцию за `RLock`.

Всего в проекте 33 теста. Рабочие данные локального Redis тестами не изменяются.

## Ограничения учебной версии

- нет регистрации и полноценной системы безопасности;
- пароль демонстрационного пользователя не хэшируется;
- уведомления поддерживают создание и чтение, но не полный CRUD;
- режимы согласованности хранятся в памяти одного экземпляра приложения;
- отключение реплик предназначено только для лабораторного эксперимента.
