# Архитектура backend

Backend построен на Java 25 и Spring Boot 4.1.1. PostgreSQL хранит постоянные
пользовательские данные и справочник категорий, Redis отвечает за уведомления,
кэш, временные данные, блокировки и эксперимент с репликацией.

Схема PostgreSQL изменяется версионированными миграциями Flyway. Hibernate
использует `ddl-auto=validate`: при несовпадении модели и схемы приложение
останавливается, а не меняет production-базу автоматически. Демонстрационный
`DataInitializer` включается отдельным параметром и отключён в production.

## Структура

```text
src/main/java/org/seitmolabs/
├── common/
│   ├── dto/                         # общие структуры запросов
│   └── exceptions/                  # единая обработка ошибок REST
├── config/
│   ├── DataInitializer.java         # пользователи, категории и учебный каталог
│   ├── OpenApiConfig.java           # Swagger и заголовки входа
│   ├── RedissonConfig.java          # клиент распределённой блокировки
│   └── WebConfig.java               # CORS и проверка ролей
└── modules/
    ├── auth/                         # демонстрационный вход без Spring Security
    ├── user/                         # пользователь и GET /users/me
    ├── catalog/                      # фильмы, залы, места и сеансы
    ├── notification/                 # Redis-уведомления и PostgreSQL outbox
    ├── categories/                   # PostgreSQL + cache-aside в Redis
    ├── booking/                      # удержания, заказы, билеты и блокировки мест
    ├── product/                      # товары кинобара
    └── consistency/                  # настраиваемая Redis-топология и эксперименты
```

Каждый предметный модуль разделён на небольшие части:

- `controller` принимает HTTP-запрос и формирует ответ;
- `service` содержит последовательность действий сценария;
- `repository` работает с PostgreSQL или Redis;
- `domain` содержит модель;
- `dto` содержит внешние структуры запросов и ответов.
- `factory` создаёт объекты с предметными инвариантами;
- `mapper` преобразует внутренние модели в REST DTO.

## Прохождение запроса

Защищённый запрос сначала проходит через `SimpleAuthFilter`. Фильтр читает
`X-Username` и `X-Password`, проверяет пользователя через PostgreSQL и кладёт
его в атрибут запроса. Затем `RoleAuthorizationInterceptor` проверяет аннотацию
`RequireRole` у административных контроллеров. Отказ в доступе возвращается как
`403`. Контроллер получает текущего пользователя, вызывает сервис, а сервис
обращается к одному или нескольким репозиториям.

Spring Security и JWT намеренно не используются: для лабораторной оставлена
прозрачная схема, которую легко показать и объяснить. Пароли хранятся открыто
только в демонстрационной среде и не подходят для production.

## Распределение данных

| Данные | Хранилище | Представление |
| --- | --- | --- |
| Пользователи | PostgreSQL | таблица `app_users` |
| Фильмы | PostgreSQL | таблица `movies` |
| Залы и места | PostgreSQL | таблицы `auditoriums`, `seats` |
| Сеансы | PostgreSQL | таблица `screenings` |
| Категории | PostgreSQL | таблица `categories` |
| Кэш категории | Redis | `category:{id}` → JSON, TTL 5 минут |
| Кэш списка категорий | Redis | `category:all` → JSON, TTL 5 минут |
| Уведомление | Redis | `notification:{id}` → JSON |
| Индекс уведомлений клиента | Redis | `notification:user:{username}` → Sorted Set |
| Счётчик уведомлений | Redis | `notification:seq` → число |
| Удержание мест | Redis | `hold:{holdId}` и `seat-hold:{screeningId}:{seatId}` с TTL |
| Заказы, билеты, кинобар | PostgreSQL | нормализованные таблицы и снимки цен |
| Блокировки оформления | Redis/Redisson | `booking:seat:{screeningId}:{seatId}` |
| События доставки | PostgreSQL | таблица `outbox_events` |
| Экспериментальные значения | Redis primary/replicas | `consistency:{key}` |

JSON выбран для объектов, потому что он сохраняет модель целиком и остаётся
читаемым через `redis-cli`. Sorted Set позволяет хранить ID уведомлений в
порядке времени создания без полного просмотра всех ключей.

PostgreSQL хранит файлы в Docker volume с фиксированным именем
`nosql-sem5-lab1_postgres_data` или значением `POSTGRES_VOLUME_NAME`. Имя не
зависит от Compose project name, поэтому новая сборка приложения использует те
же данные. Создание схемы и её последующие изменения не связаны с жизненным
циклом контейнера.

## Каталог кинотеатра

Каталог разделён на `movie`, `auditorium`, `seat` и `screening`. Постоянная
конфигурация места принадлежит залу и уникальна по залу, ряду и номеру. Сеанс
связывает фильм, зал, время начала и базовую цену.

Статус доступности не хранится в `Seat`, потому что одно физическое место имеет
разное состояние на разных сеансах. `CatalogService` получает места зала, а
`SeatAvailabilityResolver` добавляет статус для выбранного сеанса: `HELD` из
Redis и `BOOKED` из PostgreSQL имеют приоритет над `AVAILABLE`.

Методы каталога возвращают только неархивные фильмы и будущие сеансы со статусом
`SCHEDULED`. DTO отделены от JPA-сущностей, поэтому ленивые связи и внутренняя
структура таблиц не попадают в REST-ответ. `SeatLayoutFactory` создаёт схему мест
зала, `ScreeningFactory` проверяет обязательные параметры сеанса, а
`CatalogResponseMapper` централизует сборку ответов API.

## Уведомления

При создании уведомления Redis-команда `INCR` выдаёт новый ID. Затем Lua-скрипт
одной атомарной операцией:

1. сохраняет JSON по ключу `notification:{id}`;
2. добавляет ID в Sorted Set пользователя.

Это не позволяет получить уведомление без индекса или индекс без объекта.
Список читается от новых уведомлений к старым. `NotificationFactory` собирает
согласованную Redis-модель. Клиент читает только свои уведомления, а ручная
отправка вынесена в административный `/api/v1/admin/notifications`.

Системные события `SEAT_HOLD_CREATED`, `ORDER_CONFIRMED` и `ORDER_CANCELLED`
сохраняются в `outbox_events`. Планировщик повторяет недоставленные записи, а
Lua-операция использует `notification:event:{eventId}` для защиты от дублей.

## Cache-aside для категорий

PostgreSQL является источником истины. Чтение категории выполняется так:

1. сервис проверяет `category:{id}` в Redis;
2. при cache hit сразу возвращает объект и оставшийся TTL;
3. при cache miss читает PostgreSQL и записывает результат в Redis на 5 минут.

Обновление категории сразу заменяет её кэш и удаляет `category:all`. Удаление
категории очищает обе кэшированные записи. Поэтому старое значение не остаётся
доступным после изменения источника.

## Удержание и подтверждение заказа

Lua-скрипт атомарно проверяет и создаёт общий `hold:{holdId}` и ключи всех мест
с единым серверным TTL. Схема зала объединяет активные удержания Redis и
подтверждённые билеты PostgreSQL.

Подтверждение берёт `RLock` каждого места в стабильном порядке, повторно
проверяет удержание и выполняет PostgreSQL-транзакцию. Частичный уникальный
индекс для активных билетов остаётся окончательной защитой от двойной продажи.
Идемпотентный ключ уникален в пределах пользователя, а цены копируются в билет
и позицию кинобара.

## Репликация и согласованность

Docker Compose запускает primary Redis и две асинхронные реплики. Приложение
получает список узлов из `app.redis-topology.nodes`, поэтому сервисы не зависят
от их количества и имён. `RedisNodeClientFactory` создаёт подключения,
`RedisNodeRegistry` владеет ими, а `RoundRobinReplicaSelectionStrategy` выбирает
доступную реплику. Обычные записи выполняются только в узле с ролью `PRIMARY`.

- `PRIMARY` читает актуальное значение из primary;
- `REPLICA_PREFERRED` по очереди читает реплики и при недоступности использует
  primary;
- `ASYNC` отвечает после записи в primary;
- `WAIT_FOR_REPLICAS` выполняет `WAIT` на том же соединении, что и запись.

`NodeProbeService` отвечает только за чтение и диагностику узлов, а
`ReplicationTopologyService` — за команды attach/detach. API адресует узел его
стабильным `nodeId`. Диагностические методы позволяют отключить реплику командой
`REPLICAOF NO ONE`, увидеть устаревшее значение и подключить её обратно. `WAIT`
уменьшает окно рассогласования, но не создаёт транзакцию между узлами и не
гарантирует запись на диск.

## Персистентность

Primary сохраняет данные в подключённой папке `redis_data/`:

- AOF включён с `appendfsync everysec`;
- RDB-снимки создаются по расписанию;
- AOF автоматически переписывается и использует RDB-преамбулу;
- после перезапуска primary загружает сохранённые данные, а реплики повторно
  синхронизируются с ним.

## Ошибки и Swagger

`GlobalExceptionHandler` преобразует исключения в единый JSON-ответ со статусом,
сообщением и путём запроса. Основные статусы: `400`, `401`, `403`, `404`, `409`,
`500`.

SpringDoc строит OpenAPI из реальных контроллеров. Swagger UI содержит два
глобальных API-key поля: `X-Username` и `X-Password`. Метод входа и сама
документация доступны без этих заголовков.

## Тестирование

Unit-тесты изолированно проверяют сервисы и HTTP-фильтр. Интеграционный набор
через Testcontainers поднимает отдельный Redis и проверяет реальные команды:

- атомарное сохранение уведомления и индекса;
- истечение TTL-блокировки;
- кэш категории и списка;
- конкуренцию за `RLock`.

Всего в проекте 33 теста. Рабочие данные локального Redis тестами не изменяются.

## Ограничения учебной версии

- нет регистрации и полноценной системы безопасности;
- пароль демонстрационного пользователя не хэшируется;
- до реализации заказов все места сеанса возвращаются как `AVAILABLE`;
- уведомления поддерживают создание и чтение, но не полный CRUD;
- режимы согласованности хранятся в памяти одного экземпляра приложения;
- отключение реплик предназначено только для лабораторного эксперимента.
