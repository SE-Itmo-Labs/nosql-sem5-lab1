# План лабораторной работы №2 — MongoDB и сохранение Redis

Дата: 17 ноября 2026 года. Вариант: **689**.
Документ фиксирует исходное состояние проекта и план миграции.

## 1. Цель и границы

Доработать существующий кабинет кинотеатра: использовать MongoDB для постоянного
хранения, сохранить работающие Redis-механизмы первой лабораторной и выполнить
все требования варианта №689.

По последнему пожеланию владельца целевой результат включает **замену PostgreSQL
на MongoDB для постоянных данных приложения**. Это более широкий объём, чем
буквальное требование README «перенести основные объекты»: полное удаление
PostgreSQL из рабочего контура — выбранная граница проекта, а не отдельное
прямое требование задания.

Работу разделяем на два направления:

1. Замена PostgreSQL: пользователи, каталог, категории, товары, заказы, билеты,
   позиции заказа и постоянный outbox.
2. Требования варианта: документ основного объекта, вложенный журнал, связанная
   коллекция правил, транзакция, запросы, индексы, аналитика, миграция и кэш.

Первое направление само по себе не закрывает второе. Замена только PostgreSQL
с сохранением уведомлений исключительно в Redis оставит неразрешённым вопрос
переноса основного объекта первой ЛР — уведомления — в MongoDB.

### 1.1 Предлагаемое решение по уведомлениям

**Предложение для утверждения:** MongoDB хранит постоянный документ уведомления;
Redis сохраняет существующие key-value-механизмы и совместимое представление
уведомления там, где оно требуется для демонстрации первой ЛР. MongoDB является
источником истины; Redis-представление — восстанавливаемая проекция, а не вторая
независимая база истины.

Это не означает повторить предыдущую попытку и просто удалить Redis-репозиторий.
Сначала определяем контракт, роль Redis, восстановление проекции и поведение при
ошибках; затем реализуем переход вместе с заменой PostgreSQL.

Альтернатива — оставить уведомления только в Redis, а объектом второй ЛР сделать
заказ. Её допустимость нужно отдельно подтвердить по условиям курса, поскольку
основной объект первой ЛР был уведомлением. Этот план не считает её автоматически
эквивалентной выполнению задания.

### 1.2 Что сохраняем

- Существующие URL, HTTP-методы, права доступа и форматы старых CRUD-ответов.
- Числовые ID существующих сущностей в Java и frontend.
- Сценарий «фильм → сеанс → места → удержание → заказ → уведомление».
- Redis TTL, Lua-операции удержания, кэш категорий, Redis Stream событий удержания.
- Лабораторные эксперименты Redis primary/replica и персистентность Redis.
- Правила отмены, снимки цен и идемпотентность оформления.

Не включаем в эту работу новую платёжную систему, новый дизайн, замену схемы
аутентификации и произвольные дополнительные административные функции.

## 4. Целевая архитектура хранения

| Данные | Постоянный источник | Роль Redis |
| --- | --- | --- |
| Пользователи | `users` в MongoDB | Не требуется |
| Фильмы, залы, места, сеансы | MongoDB | Удержания мест конкретного сеанса |
| Категории | `categories` в MongoDB | Существующий cache-aside |
| Товары | `products` в MongoDB | Не требуется |
| Заказы, билеты, позиции | MongoDB | Координация оформления, временные удержания |
| Уведомления | `notifications` в MongoDB | Совместимая проекция и кэш MongoDB-запроса |
| Правила обработки | `processing_rules` в MongoDB | Не требуется |
| События заказа | `outbox_events` в MongoDB | Доставка в Redis-проекцию |
| События удержания | Существующий Redis Stream до обработки | Сохраняется текущая атомарная запись с удержанием |
| Метаданные схемы/миграций | `schema_migrations` в MongoDB | Не требуется |
| Счётчики числовых ID | `sequences` в MongoDB | Старые счётчики учитываются при переносе |

PostgreSQL удаляется из рабочего подключения только после переноса последнего
потребителя. Его volume и резервные копии не удаляются автоматически.

### 4.1 Документная модель без механического копирования JPA

На первом переходе разумно сохранить отдельные коллекции `users`, `movies`,
`auditoriums`, `seats`, `screenings`, `categories`, `products`, `orders`,
`tickets`, `order_products`. Это уменьшает объём одновременного изменения
предметной логики и сохраняет понятное ограничение активных билетов.

Вместо JPA-связей хранятся явные ID: `userId`, `movieId`, `auditoriumId`,
`screeningId`, `orderId`, `seatId`, `productId`. Не переносим ленивые proxy,
`getReferenceById`, JPQL и каскады JPA в MongoDB-модель.

DTO собираются mapper-сервисами с пакетной загрузкой связанных данных,
без N+1-запросов. Объединять все сущности в один документ не нужно. Снимки цен
остаются снимками; деньги сохраняются как Decimal128 с согласованным масштабом,
время — как BSON Date в UTC, ID — как BSON long.

Обязательные связи проверяются сервисом: MongoDB-ссылки не заменяют внешние
ключи SQL. Удаление используемого справочника запрещается либо заменяется
архивированием по явно выбранному правилу.

### 4.2 Совместимость ID

Существующие числовые ID сохраняются. Для новых записей используется отдельный
атомарный счётчик по типу сущности в `sequences` с `$inc` и возвратом нового
значения. `@Id Long` сам по себе последовательность не генерирует.

При переносе начальное значение каждого счётчика должно быть не меньше
максимального перенесённого ID. Для уведомлений дополнительно учитывается
существующий `notification:seq`. На время переключения выдачи ID останавливаем
старые записи; два независимых генератора одновременно не используются.

Промежутки в последовательности допустимы. Уникальность обеспечивается `_id`.
Если ID выдаётся внутри повторяемой транзакции, повтор не должен приводить
к повторному созданию бизнес-операции.

Для уведомлений счётчик хранится в документе с `_id: "notifications"` в
коллекции `sequences`. Приложение при старте поднимает счётчик до максимального
числового `_id` в `notifications` и атомарно увеличивает его перед вставкой.
Частичный уникальный индекс по `sourceEventId` защищает от повторной записи
того же события outbox.

## 5. Модель требований варианта

### 5.1 Документ уведомления

Сохраняются старые поля `id`, `userId` (в текущем API это username), `title`,
`text`, `categoryId`, `status`, `createdAt`, `sourceEventId`. Добавляются:

| Поле | Назначение |
| --- | --- |
| `updatedAt` | Время последнего изменения документа |
| `processingRuleId` | ID применённого правила либо `null` |
| `processingRuleVersion` | Версия правила, по которой выполнено применение |
| `tags` | Массив уникальных непустых нормализованных строк |
| `actionLog` | Массив типизированных записей истории |
| `schemaVersion` | Версия структуры документа |
| `version` | Версия для защиты от потери конкурентных изменений |

Элемент журнала: `actionId`, `type`, `actorId`, `at`, ограниченные типизированные
детали действия. Не записываем пароли, заголовки авторизации и произвольные
полные HTTP-запросы. Время и исполнитель определяются сервером.

Действия: `CREATED`, `READ`, `RULE_APPLIED`, `TAGS_CHANGED`. Повторная отметка
уже прочитанного уведомления не порождает неограниченный поток одинаковых записей.
Журнал меняется атомарно вместе со статусом/метками и `updatedAt`, через
операторы обновления и проверку ожидаемой версии/статуса, а не безусловную
перезапись старого снимка всего документа.

Нужно выбрать ограничение числа записей и длины полей до реализации: BSON имеет
лимит размера документа. Предложение для учебной системы — до 500 записей;
при достижении лимита явная ошибка, без молчаливой потери истории. Отдельный
архив журнала — последующее расширение, не подмена обязательного вложения.

### 5.2 Правила обработки

Коллекция `processing_rules`:

- числовой ID, уникальный код, название, описание;
- `enabled`, версия, время создания/изменения;
- условия применимости: категория и разрешённый тип события;
- действие: назначение набора меток;
- `appliedCount` и `lastAppliedAt` как сведения о применении.

Пример: правило `BOOKING_CONFIRMED` для уведомлений о подтверждённом заказе
назначает метки `booking`, `confirmed`.

Правила определяют проверяемое поведение, а не произвольный JavaScript из БД.
Редактирование доступно администратору. Используемое правило отключается,
а не физически удаляется с разрушением истории.

### 5.3 Обязательная транзакция

Сценарий: администратор применяет подходящее правило к уведомлению.

В одной MongoDB-транзакции:

1. Проверить роль, существование уведомления и активность/версию правила.
2. Проверить применимость правила и уникальность идентификатора команды.
3. Увеличить `appliedCount`, изменить `lastAppliedAt` у правила.
4. Обновить метки, ссылку и версию правила, `updatedAt` уведомления.
5. Добавить `RULE_APPLIED` в его вложенный журнал.
6. Обновить версию инвалидируемого кэша и записать событие обновления
   Redis-проекции, если она используется.
7. Зафиксировать транзакцию.

Искусственная ошибка между шагами 3 и 5 должна откатить оба документа.
Повтор одной команды не увеличивает счётчик и журнал второй раз: запись
идемпотентности с уникальным ключом команды фиксируется в той же транзакции.
Изменение только уведомления не считается выполнением требования об изменении
связанной сущности.

### 5.4 Реализация пункта 2

Журнал `notifications.actionLog` хранится в документе уведомления. При отправке
записывается `CREATED` с именем администратора или значением `system`.
При первом переходе в `READ` добавляется запись с именем получателя.
Для старых документов без журнала история начинается со следующего действия.
Журнал и служебные поля правила доступны в MongoDB. Формат прежнего HTTP-ответа сохраняется.

При `APP_DATA_INITIALIZER_ENABLED=true` создаётся демонстрационное правило
`processing_rules` с `_id: 7`. Для проверки нужно подтвердить новый заказ,
дождаться уведомления и от имени администратора вызвать
`POST /api/v1/admin/notifications/{id}/apply-rule` с телом `{"ruleId":7}`.
Правило подходит для уведомлений с `sourceEventType: "ORDER_CONFIRMED"`.
Старые уведомления без типа исходного события остаются доступны для чтения и удаления.

Сервис записывает метки `booking` и `confirmed`, `processingRuleId: 7`
и событие `RULE_APPLIED` в уведомление одной атомарной операцией. Повторное
применение текущего правила не дублирует запись в журнале. Для демонстрации
можно прочитать оба документа в `mongosh`, подставив числовой ID уведомления.

```javascript
db.notifications.findOne({ _id: ID_УВЕДОМЛЕНИЯ }, { actionLog: 1, processingRuleId: 1, tags: 1 })
db.processing_rules.findOne({ _id: 7 })
```

Межколлекционная транзакция из раздела 5.3 остаётся отдельным этапом.

## 6. MongoDB-инфраструктура и транзакции

- MongoDB запускается как replica set. Для локальной ЛР допустим одноузловой
  replica set; это не отказоустойчивый production-кластер.
- Инициализация replica set, коллекций, индексов и валидаторов воспроизводится
  из версионированного кода/конфигурации проекта, без ручных действий в mongosh.
- Проверяется доступность объявленного адреса узла и из IDE, и из Compose:
  одной замены `localhost` в URI недостаточно, если discovery возвращает
  недоступное имя узла.
- Настраиваются healthcheck с проверкой готовности primary, volume, URI,
  локальные порты и параметры окружения.
- Для MongoDB создаётся явно именованный `MongoTransactionManager`; в период
  сосуществования PostgreSQL менеджер каждого сценария выбирается явно.
- Все операции одной транзакции используют одну сессию MongoDB. Redis-команды
  не считаются частью MongoDB-транзакции.
- Коллекции, индексы и схемы готовятся до бизнес-транзакций.
- Для конфликтов записи и неоднозначного результата commit выбирается
  ограниченная политика retry, учитывающая метки ошибок драйвера. Побочные
  внешние эффекты не выполняются внутри повторяемого тела транзакции.

Для существующей Raspberry Pi 5 / 6 ГБ RAM не утверждаем заранее достаточность:
после переноса измеряем память Java, MongoDB и Redis вместе, задержки и работу
диска при ожидаемой конкуренции. Несколько MongoDB-процессов на той же плате
не обеспечивают независимую отказоустойчивость. Во время перехода одновременная
работа PostgreSQL и MongoDB дополнительно увеличивает расход памяти.

## 7. Перенос бронирования и гарантий целостности

### 7.1 Подтверждение заказа

Redis удерживает места как сейчас. Источник постоянной занятости переносится
в MongoDB. В транзакции создаются заказ, билеты, позиции товаров и outbox.

Обязательные индексы:

| Коллекция | Индекс/ограничение |
| --- | --- |
| `users` | Уникальный `username` |
| `movies` | Уникальный `slug` |
| `seats` | Уникальные `(auditoriumId, rowNumber, seatNumber)` |
| `orders` | Уникальные `(userId, idempotencyKey)` и `holdId` |
| `tickets` | Частичный уникальный `(screeningId, seatId)` для `status=CONFIRMED` |
| `order_products` | Уникальные `(orderId, productId)` |
| `processing_rules` | Уникальный код |
| `notifications` | Частичный уникальный строковый `sourceEventId` |
| Квитанции доставки | Уникальный ID исходного события |

Это перенос требований SQL-ограничений, а не только замена синтаксиса запроса.
Нельзя обеспечить двойную продажу проверкой «прочитать свободно → вставить».
Частичный уникальный индекс остаётся окончательной защитой при гонке.

Распределённую блокировку первой ЛР нужно восстановить/проверить отдельно:
в текущем коде её вызов закомментирован. Ключи берутся в стабильном порядке;
MongoDB-транзакция и уникальные индексы сохраняют гарантии при сбое блокировки.

Redis-удержание освобождается только после commit. Ошибка освобождения не
отменяет подтверждённый заказ: занятость берётся из билетов, очистка повторяется
либо завершается по TTL. Повтор запроса с тем же ключом возвращает прежний заказ.

### 7.2 Отмена

SQL `PESSIMISTIC_WRITE` заменяется условным обновлением/версией документа
заказа в MongoDB. Проверка владельца и срока отмены, изменение статусов билетов
и событие отмены входят в одну транзакцию. Два параллельных запроса отмены
создают одно бизнес-событие. Отменённые билеты сохраняются в истории и перестают
участвовать в частичном уникальном индексе активной продажи.

## 8. Redis, outbox и совместимость уведомлений

Все существующие key-value-сценарии остаются рабочими. Выделяем два назначения:
временные/координационные данные Redis и проекции постоянных MongoDB-данных.

Событие заказа сохраняется в MongoDB вместе с заказом. Событие удержания
по-прежнему атомарно записывается в Redis Stream вместе с удержанием. Обработчик
создаёт постоянное уведомление в MongoDB, после чего подтверждает обработку
исходного события. Повтор после сбоя безопасен.

MongoDB-изменение уведомления и запись события обновления Redis-проекции
фиксируются вместе. Обновление Redis выполняется после commit с повторами.
Старое событие проекции не должно перезаписывать более новую версию документа.
Чтение с отстающей Redis-реплики не используется для решений о доступе и покупке.

Для сохранения прежних Redis-ключей `notification:{id}` и пользовательского
Sorted Set можно оставить текущие Lua-операции как реализацию проекции.
Их смысл и названия при необходимости уточняются, но они не удаляются до
готовности и проверки замены. При miss чтение восстанавливается из MongoDB.
После клиентской мутации read-after-write берётся из MongoDB или проверенной
актуальной версии проекции; асинхронную доставку не выдаём за мгновенную.

Квитанция обработанного события должна сохраняться независимо от документа
уведомления: удаление уведомления пользователем не разрешает повторной доставке
восстановить его. Удаление также доставляет версионированное событие в проекцию.
Тестируется окно «уведомление сохранено, подтверждение outbox не выполнено».

## 9. Контракт серверного поиска и frontend

Существующий `GET /api/v1/notifications` без параметров продолжает возвращать
массив. Не заменяем этот ответ на `Page`, ломая старых клиентов.

Контракт и запланированные дополнения:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/notifications/search` | Поиск своих уведомлений с метаданными страницы |
| GET | `/api/v1/notifications/analytics/top-tags` | Частота меток своих уведомлений |
| GET/POST | `/api/v1/admin/processing-rules` | Просмотр и создание правил |
| GET/PUT | `/api/v1/admin/processing-rules/{id}` | Чтение и редактирование правила |
| POST | `/api/v1/admin/processing-rules/{id}/disable` | Отключение правила |
| POST | `/api/v1/admin/notifications/{id}/apply-rule` | Применение правила с ID команды |

### 9.1 Реализация пункта 3

`GET /api/v1/notifications/search` ищет уведомления пользователя из запроса
авторизации. Ответ содержит `items`, `page`, `size`, `totalElements` и
`totalPages`. В элементах доступны `updatedAt`, `processingRuleId` и `tags`.

| Параметры | Значения |
| --- | --- |
| `processingRuleId`, `categoryId`, `status`, `tag` | Точное совпадение с полем или элементом массива `tags` |
| `updatedFrom`, `updatedTo` | Даты ISO 8601, интервал `[from, to)` |
| `actionType`, `actorId` | `$elemMatch` по одной записи журнала |
| `page`, `size` | Нумерация с нуля, размер от 1 до 100, по умолчанию 20 |
| `sort` | `UPDATED_AT_DESC` по умолчанию, также `UPDATED_AT_ASC`, `CREATED_AT_DESC` и `CREATED_AT_ASC`. ID разрешает совпадения дат |

При старте для старых записей с датой создания заполняется `updatedAt` из
`createdAt`. Новые уведомления получают обе даты при создании. Прочтение
и применение правила обновляют `updatedAt` вместе с журналом.

С демо-данными запрос `?actionType=RULE_APPLIED&actorId=admin&page=0&size=1`
от имени `user` возвращает один результат с метаданными страницы. С теми же
фильтрами и `page=1` можно получить следующий результат. Запрос
`?actionType=READ&actorId=admin` исключает уведомления, у которых `READ` сделал
получатель, даже если администратор применял к ним правило.

Подсчёт и выборка страницы выполняются отдельными запросами к MongoDB.
Набор результатов может измениться между запросами при параллельных записях.

Frontend меняется после стабилизации API: серверные фильтры/страницы, отображение
журнала, меток и правил, защищённый экран администрирования. HTTP/mock имеют
одинаковую семантику. Числовые ID сохраняются, массовый переход на `string`
не требуется. Ошибка реального API не подменяется mock-результатом.

## 10. Индексируемый запрос и аналитика

### 10.1 Составной индекс

Основной запрос: уведомления текущего пользователя по правилу и диапазону
`updatedAt`, с устойчивой сортировкой. Предлагаемый индекс:

`{ userId: 1, processingRuleId: 1, updatedAt: -1, _id: -1 }`.

`userId` входит первым из-за обязательного ограничения владельцем. Если нужен
отдельный запрос по правилу без пользователя, для него отдельно обосновывается
другой индекс; существующий индекс не считается универсальным.

Эксперимент выполняется на изолированной базе с воспроизводимым генератором:
например, 100 000 уведомлений, несколько пользователей и правил, разные даты.
Фиксируем размер, распределение и селективность. Сначала `explain("executionStats")`
без целевого индекса, затем создание индекса и тот же запрос с ним.

Сохраняем планы, `nReturned`, `totalDocsExamined`, `totalKeysExamined`, наличие
COLLSCAN/IXSCAN и блокирующей сортировки, время серии запусков. Прогрев и версия
БД одинаковы. Не обещаем выигрыш по одной миллисекундной цифре; ключевое
доказательство — снижение объёма просмотренных данных и подходящий план.
Тестовые эксперименты не удаляют индексы рабочей базы.

### 10.2 Популярные метки

Pipeline: `$match` по владельцу/дате → `$unwind: "$tags"` → `$group` по метке
с подсчётом → `$sort` по частоте и имени → `$limit`.

Семантика: число уведомлений, содержащих метку. Массив хранит уникальные метки;
для старых данных перед подсчётом устраняются повторы внутри одного документа.
Пустые/отсутствующие метки не учитываются, равные частоты сортируются стабильно.
Контрольный набор имеет заранее рассчитанный ожидаемый результат.

## 11. JSON Schema и повторяемая миграция

Настройку коллекций, валидаторов и индексов выполняет версионированный Java-код
или отдельная команда проекта. Ручные действия в консоли БД не являются
обязательной частью запуска. Flyway SQL не считается готовым средством миграции
MongoDB; нужен отдельный механизм с историей и защитой от параллельного старта.

### 11.1 Переход структуры `tag` → `tags`

1. Подготовить валидные документы v1 с одиночным `tag` и документы v2 с `tags`.
   Восстановленный проект вообще не имеет меток: v1 создаётся осмысленным
   набором старого формата для эксперимента, а не объявляется существующим фактом.
2. На переходный период валидатор допускает явно определённые v1 и v2.
3. Миграция выбирает только старые/смешанные документы; непустой `tag`
   переносится в массив без потери уже имеющегося `tags` и без дублей.
4. Нормализовать метки, удалить `tag`, выставить `schemaVersion=2`.
5. Если оба поля отсутствуют, записать пустой массив. Неверные типы вынести
   в отчёт ошибок; не уничтожать их молчаливо.
6. Работать ограниченными пакетами, сохранять счётчики и возможность продолжения
   после остановки. Запретить параллельные старые записи либо включить
   совместимый writer на время перехода.
7. Проверить отсутствие v1 и включить строгий валидатор v2.
8. Повторить миграцию: изменено 0 документов, данные и журнал не продублированы.

Это отдельный эксперимент изменения схемы, а не то же самое, что перенос
PostgreSQL → MongoDB.

### 11.2 Валидатор v2

Проверяет BSON-типы, обязательные поля, допустимые статусы, массив строк `tags`,
структуру `actionLog`, даты и версию схемы. Для связанных коллекций проверяются
их собственные поля. `@Valid` проверяет HTTP-запрос, но не заменяет JSON Schema
на стороне MongoDB; `@Indexed` не заменяет реально созданный индекс.

На защите прямой неверный документ должен отклоняться БД. Ссылочную целостность
между коллекциями JSON Schema не обеспечивает — это обязанность сервиса и
транзакционных сценариев.

## 12. Redis-кэш запроса к MongoDB

Отдельно от существующего кэша категорий кэшируем результат
`GET /notifications/search`. Начальный TTL — 60 секунд, параметр конфигурации.

Ключ включает версию формата, текущего владельца, версию данных, нормализованные
фильтры, диапазон дат, сортировку и страницу. Пароли не входят в ключ. Результат
одного пользователя никогда не используется для другого. Ошибки не кэшируются.

Чтобы устаревший запрос не вернул старый результат после инвалидации,
предлагается поколение данных пользователя, хранимое в MongoDB:

- каждая мутация уведомлений увеличивает поколение в той же MongoDB-транзакции;
- чтение получает актуальное поколение из primary и ищет Redis-ключ с ним;
- cache miss выполняет запрос и кэширует результат под прочитанным поколением;
- устаревший конкурентный запрос может записать только ключ старого поколения,
  который новые чтения уже не используют; TTL удаляет его позднее.

Это оставляет небольшое чтение метаданных MongoDB на cache hit, но исключает
загрузку/сортировку всего результата и не зависит от мгновенной outbox-инвалидации.
Произвольный `SCAN` по всем ключам не является штатной инвалидацией.

При недоступном Redis чтение выполняется из MongoDB без кэша. Недоступность
MongoDB не должна автоматически возвращать устаревшие данные как свежие.
Проверяем MISS/HIT, TTL, создание/чтение/удаление/применение правила, гонку
«старый cache miss одновременно с мутацией» и изоляцию пользователей.

| 10 | Кэш MongoDB-запроса с TTL и версионированием | Проверены инвалидация, конкурентный miss и недоступность Redis |

Каждая итерация имеет небольшой согласованный набор изменений и собственную
проверку. В переходный период интерфейсы репозиториев изолируют смену хранилища;
один бизнес-сценарий не растягивается на несогласованные PostgreSQL- и
MongoDB-транзакции. Перенос транзакционной группы заказа выполняется вместе.

Это несколько содержательных этапов, а не массовая замена аннотаций.
Самые трудоёмкие участки — оформление, outbox, перенос данных и проверка гонок.
Точную оценку времени уточняем после утверждения модели; обещание фиксированного
числа часов до этих решений было бы необоснованным.

## 14. Проверки, перенос данных и выход из PostgreSQL

### 14.1 Набор проверок

- Unit: применение правил, нормализация меток, права и владение, преобразование DTO.
- Контрактные HTTP: старые URL/методы/поля/типы ID и новые query-параметры.
- MongoDB integration на replica set: реальная запись, индексы, rollback,
  конфликты версий, частичная уникальность билетов, повтор событий.
- Redis integration: прежние Lua/TTL/Stream/кэш и восстановление проекций.
- Совместные: commit заказа при временной недоступности доставки; повтор после
  сохранения уведомления; удаление уведомления до повтора; отмена дважды;
  пересекающиеся покупки, истечение удержания и повтор ключа идемпотентности.
- Миграционные: смешанные v1/v2, неверные типы, остановка в середине, повторный запуск.
- Frontend: lint, TypeScript, сборка и проверка HTTP/mock-семантики.
- Персистентность: данные остаются после пересоздания контейнера; backup/restore
  проверяется на отдельной базе.

Testcontainers использует изолированные MongoDB/Redis и не подключается к
рабочим базам. Если Docker недоступен, это блокировка проверки, а не основание
считать интеграционные тесты пройденными. Для JDK 25 заранее проверяется
подключение Mockito-agent. Тестовые серверы приложения без запроса не запускаются.

### 14.2 Перенос существующих данных

До реализации выбирается: сохраняем текущие данные или создаём только новый
учебный набор. Сброс никогда не является подразумеваемым вариантом.

При сохранении данных:

1. Сделать проверяемые резервные копии PostgreSQL и Redis.
2. Подготовить повторяемую команду экспорта/импорта, сохраняющую ID, связи,
   статусы, даты, цены, idempotency keys, outbox и уведомления Redis.
3. Сверить количество документов, ссылки, суммы заказов и уникальные ограничения;
   несовместимые записи отразить в отчёте, а не пропускать молча.
4. На окончательное переключение остановить бизнес-записи и обработчики
   доставки, импортировать финальные изменения и установить счётчики ID.
5. Переключить все репозитории транзакционной группы; отключить старых writers.
6. Проверить контрольные чтения и пробную операцию, затем возобновить записи.
7. Сохранить старые volumes до принятия результата владельцем.

Откат до открытия записей — возврат конфигурации и прежней базы. После появления
новых записей в MongoDB одного `git revert` недостаточно: нужны обратный перенос
данных либо восстановление и повтор событий. Эту границу фиксируем заранее.

### 14.3 Окончательная очистка

Текущий Gradle-проект использует MongoDB и Redis. PostgreSQL-сервис удалён из
Compose, а переменные `POSTGRES_*` убраны из генерации `credentials.env` в CI.
SQL-миграции первой лабораторной сохранены в [архиве](archive/postgresql/).

| Нужна ли старая история/текущие данные? | Сохраняем, пока явно не выбран новый учебный набор |
| Какое правило обработки? | Назначение меток по категории/типу события; транзакционное применение |
| Какой запрос кэшируем? | Серверный поиск уведомлений текущего пользователя |
| Какая MongoDB-топология локально? | Одноузловой replica set; отдельно от production-решения |
| Сколько меток/журнала допускаем? | Предложение: до 20 меток, до 500 действий, ограниченная длина полей |

До решения этих вопросов не начинать массовое преобразование моделей.
Согласование плана не является разрешением изменять production или удалять данные.

## 16. Маршрут защиты и финальный критерий

1. Запустить согласованную конфигурацию без PostgreSQL, показать MongoDB и Redis.
2. Выполнить прежний вход, выбор мест, TTL-удержание и подтверждение заказа.
3. Показать заказ в MongoDB, временные ключи в Redis и доставленное уведомление.
4. Применить правило, показать его статистику и вложенный журнал уведомления.
5. Повторить команду, затем воспроизвести rollback искусственной ошибкой.
6. Выполнить серверный поиск по правилу, датам и вложенным полям, показать страницы.
7. Сопоставить explain до/после составного индекса на одном наборе данных.
8. Показать рейтинг меток и объяснить стадии pipeline.
9. Показать отказ JSON Schema и два запуска миграции структуры.
10. Показать cache MISS/HIT, TTL и инвалидацию после мутации.
11. Показать результаты тестов и перечислить фактические ограничения.

ЛР готова, когда каждый пункт раздела 3 имеет реализацию и воспроизводимое
доказательство, старые бизнес-сценарии и Redis продолжают работать, а рабочему
приложению больше не требуется PostgreSQL в утверждённом полном варианте переноса.
