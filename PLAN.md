# План реформы приложения кинотеатра

## 1. Зачем нужна реформа

В проекте уже реализованы основные технические требования лабораторной:

- Spring Boot backend и Nuxt frontend;
- PostgreSQL для пользователей и справочника категорий;
- Redis для уведомлений, временных данных, кэша и блокировок;
- primary Redis и две реплики для исследования согласованности;
- AOF и RDB для восстановления данных;
- unit- и интеграционные тесты.

Проблема текущей версии не в отсутствии функций, а в отсутствии единого
пользовательского процесса. Уведомления, временные блокировки, распределённые
блокировки, категории и эксперимент с репликацией существуют как отдельные
демонстрационные разделы. Пользователь не проходит связный путь клиента
кинотеатра, а технические возможности Redis слабо связаны с предметной областью.

Цель реформы — собрать существующие механизмы в работающий сценарий:

> клиент выбирает фильм и сеанс, временно удерживает места, добавляет товары
> кинобара, подтверждает заказ и получает уведомление о результате.

Требования лабораторной должны проявляться внутри этого сценария, а отдельный
лабораторный раздел должен помогать объяснить их на защите.

## 2. Принципы реализации

1. Каждая итерация завершается работающим вертикальным фрагментом: backend,
   frontend, данные, обработка ошибок и документация изменяются вместе.
2. До реализации очередной итерации фиксируются её бизнес-правила и REST-контракт.
3. PostgreSQL является источником истины для постоянных бизнес-данных.
4. Redis используется там, где нужны TTL, быстрый доступ, атомарные операции,
   кэш, координация запросов или демонстрация согласованности.
5. Постоянно занятое место защищается ограничением PostgreSQL. Распределённая
   блокировка дополняет эту гарантию, но не заменяет её.
6. Входные данные не содержат владельца операции, если он уже известен из
   текущей пользовательской сессии.
7. Модели остаются нормализованными и предметно определёнными. Не следует
   создавать один универсальный класс для фильма, места, товара и заказа.
8. Mock- и HTTP-реализации frontend поддерживают один контракт и одинаковые
   бизнес-правила.
9. Клиентские экраны показывают действия кинотеатра. Диагностика Redis находится
   в отдельном разделе «Лаборатория» и не разрывает основной путь.
10. После каждой итерации обновляются фактические документы из `docs/`. Будущее
    поведение не описывается как уже реализованное.
11. Создание предметных объектов с инвариантами выполняется через небольшие
    фабрики. Преобразование JPA-сущностей в REST DTO выполняется отдельными
    mapper-классами. Фабрика не используется как универсальная замена любому
    конструктору.
12. Конфигурация Redis-топологии не должна быть зашита в сервисы. Сервисы работают
    с реестром узлов и стратегиями выбора, не зная количество реплик заранее.
13. Каждый HTTP-метод имеет явно определённую роль: клиентскую, административную
    или лабораторную. Одной аутентификации без проверки полномочий недостаточно.

## 3. Целевой пользовательский сценарий

Основной путь клиента:

1. Клиент входит в личный кабинет.
2. Открывает афишу и выбирает фильм.
3. Выбирает сеанс и видит состояние мест в зале.
4. Выбирает одно или несколько свободных мест.
5. Система создаёт временное удержание мест с серверным TTL.
6. Клиент видит обратный отсчёт и переходит к оформлению.
7. При желании клиент добавляет товары кинобара.
8. Клиент подтверждает заказ.
9. Система повторно проверяет удержание, фиксирует заказ и билеты, освобождает
   временные ключи и создаёт уведомление.
10. Клиент видит подтверждённый заказ и новое уведомление в личном кабинете.

Негативные ветки сценария:

- место уже временно удерживается другим клиентом;
- место было окончательно куплено другим клиентом;
- срок удержания истёк до подтверждения;
- клиент пытается подтвердить чужое удержание;
- повторный запрос подтверждения не должен создавать второй заказ;
- часть выбранных товаров стала недоступна;
- уведомление временно не удалось записать в Redis.

## 4. Целевая предметная модель

### 4.1 Постоянные сущности PostgreSQL

| Сущность | Назначение | Основные связи и ограничения |
| --- | --- | --- |
| `User` | Клиент кинотеатра | Уже существует; заказ принадлежит текущему пользователю |
| `Movie` | Фильм из афиши | Название, описание, длительность, возрастной рейтинг и статус показа |
| `Auditorium` | Зал кинотеатра | Содержит постоянную конфигурацию мест |
| `Seat` | Физическое место | Принадлежит залу; уникально по сочетанию зала, ряда и номера |
| `Screening` | Показ фильма | Ссылается на фильм и зал; содержит время начала и базовую цену |
| `Product` | Товар кинобара | Название, актуальная цена и признак доступности |
| `Order` | Заказ клиента | Владелец, статус, итоговая сумма, время создания и подтверждения |
| `Ticket` | Купленное место | Ссылается на заказ, сеанс и место; `(screening_id, seat_id)` уникально |
| `OrderProduct` | Позиция кинобара | Количество и снимок цены на момент оформления |
| `NotificationCategory` | Категория уведомления | Источник истины существующего cache-aside сценария |
| `OutboxEvent` | Надёжная доставка события | Хранит событие заказа до записи уведомления в Redis |

Цены билетов и товаров копируются в заказ. Изменение справочника в будущем не
должно менять сумму уже подтверждённого заказа.

### 4.2 Временная модель Redis

Одно удержание может включать несколько мест:

- `seat-hold:{screeningId}:{seatId}` → идентификатор удержания, TTL;
- `hold:{holdId}` → JSON с `userId`, `screeningId`, списком `seatIds`, временем
  создания и временем истечения, TTL;
- создание всех ключей выполняется атомарно Lua-скриптом: если занято хотя бы
  одно место, удержание не создаётся;
- TTL задаётся сервером из конфигурации, а не произвольным значением клиента;
- API возвращает `holdId`, `expiresAt` и выбранные места;
- подтверждение требует `holdId` и проверяет владельца удержания.

Для уведомлений сохраняется существующая схема:

- `notification:{id}` → JSON уведомления;
- `notification:user:{username}` → Sorted Set идентификаторов;
- `notification:seq` → атомарный счётчик.

Для справочника категорий сохраняется cache-aside:

- `category:{id}` → JSON категории с TTL;
- `category:all` → JSON списка с TTL.

Экспериментальные ключи согласованности имеют отдельный префикс и не
используются для подтверждения заказа.

## 5. Распределение ответственности между хранилищами

| Данные или операция | Источник истины | Роль Redis |
| --- | --- | --- |
| Пользователь | PostgreSQL | Не требуется |
| Фильм, зал, место, сеанс | PostgreSQL | Возможный кэш чтения после основного сценария |
| Доступность места | PostgreSQL для купленных билетов | Redis хранит активное временное удержание |
| Заказ, билет, товары заказа | PostgreSQL | Блокировка критической операции подтверждения |
| Уведомление | Redis согласно варианту лабораторной | Основное хранение и индекс по пользователю |
| Категория уведомления | PostgreSQL | Cache-aside с TTL и инвалидацией |
| Событие для уведомления | PostgreSQL outbox | После доставки создаётся уведомление в Redis |
| Эксперимент согласованности | Не относится к бизнес-данным | Primary, реплики, `WAIT` и управляемое чтение |

## 6. Целевые модули backend

Структуру следует развивать по предметным модулям:

```text
modules/
├── auth/
├── user/
├── catalog/
│   ├── movie/
│   ├── auditorium/
│   ├── seat/
│   └── screening/
├── booking/
│   ├── hold/          # временное удержание мест в Redis
│   └── order/         # заказ, билеты и позиции кинобара
├── product/           # справочник кинобара
├── notification/
├── categories/
├── consistency/
└── laboratory/        # при необходимости фасад демонстрационных операций
```

Контроллеры принимают и проверяют HTTP-запрос. Сервисы реализуют бизнес-сценарии.
Репозитории работают с одним конкретным хранилищем. Операция подтверждения заказа
координирует несколько модулей через отдельный прикладной сервис, а не помещает
всю логику в контроллер или универсальный репозиторий.

### Создание объектов и преобразование DTO

Для сокращения повторяющейся ручной сборки вводятся специализированные классы:

- `SeatLayoutFactory` строит места зала по описанию рядов и применяет правила
  типов `STANDARD`, `PREMIUM` и `ACCESSIBLE`;
- `ScreeningFactory` создаёт сеанс и проверяет обязательные связи, время и цену;
- `SeatHoldFactory` в следующей итерации создаёт согласованное удержание с
  серверным TTL, владельцем и временем истечения;
- `OrderFactory` позднее создаёт заказ из проверенного удержания и снимков цен;
- `NotificationFactory` создаёт системное или административное уведомление из
  типизированной команды;
- `CatalogResponseMapper` и mapper-классы других модулей отвечают только за
  преобразование доменных объектов в DTO.

`DataInitializer` должен описывать набор демонстрационных данных декларативно и
передавать создание фабрикам. Он не должен самостоятельно содержать правила
конструирования мест, сеансов и будущих заказов. Простые record DTO и value
objects можно создавать напрямую, если у них нет правил и необязательных полей.

### Redis-топология и исследование согласованности

Текущий `NodeProbeService` содержит отдельные поля для `primary`, `replica-1` и
`replica-2`, вручную создаёт два клиента и выбирает узел через `switch`.
`ConsistencyService` дополнительно предполагает ровно две реплики и переключает
их выражением `% 2`. Это необходимо заменить следующей моделью:

- `RedisTopologyProperties` читает из конфигурации список узлов с `id`, `role`,
  `host` и `port`;
- `RedisNodeId` является типизированным идентификатором, а `RedisNodeRole`
  содержит роли `PRIMARY` и `REPLICA`;
- `RedisNodeClientFactory` создаёт клиент и его ресурсы из описания узла;
- `RedisNodeRegistry` владеет клиентами и позволяет получить primary, конкретный
  узел или список доступных реплик;
- `ReplicaSelectionStrategy` определяет выбор реплики; первая реализация —
  `RoundRobinReplicaSelectionStrategy`;
- `NodeProbeService` только читает значение, TTL и `INFO` выбранного узла;
- `ReplicationTopologyService` выполняет административные операции attach/detach;
- `ConsistencyService` оркестрирует эксперимент через эти абстракции и не знает
  ни имён, ни количества реплик.

В API узел адресуется стабильным `nodeId`, например `primary` или
`replica-eu-1`, а не числом `1/2`. Термин `MASTER` в новых контрактах заменяется
на `PRIMARY`; старое входное значение можно временно принять как alias для
совместимости. Добавление третьей реплики должно требовать только изменения
конфигурации.

## 7. Роли и границы доступа

В системе остаются две предметные роли: `CLIENT` и `ADMIN`. Текущее значение
`ROLE_USER` при миграции переименовывается или однозначно сопоставляется роли
`CLIENT`.

### Клиент

Клиент может:

- просматривать афишу, сеансы и доступность мест;
- создавать, читать и освобождать только собственные удержания;
- оформлять, читать и при допустимых правилах отменять только свои заказы;
- просматривать и отмечать прочитанными только свои уведомления;
- читать клиентские справочники без административных деталей кэша.

Клиент не передаёт `userId`, `owner` или произвольный TTL: владелец определяется
из сессии, а время жизни — серверной политикой.

### Администратор

Администратор может:

- создавать и изменять фильмы, залы, места, сеансы и товары кинобара;
- отменять сеанс и инициировать связанные системные уведомления;
- управлять категориями уведомлений;
- отправлять целевое или массовое уведомление через отдельную типизированную
  команду;
- изменять разрешённые серверные параметры, включая политику TTL удержания, в
  безопасных пределах;
- запускать лабораторные эксперименты, менять режимы согласованности и управлять
  подключением реплик.

Административные мутации располагаются под `/api/v1/admin/**`. Лабораторные
операции располагаются под `/api/v1/admin/laboratory/**` либо защищаются тем же
правилом `ADMIN`. Клиентские read-only методы каталога остаются под `/api/v1/**`.

Проверка роли выполняется до вызова бизнес-сервиса. На этапе архитектурного
рефакторинга нужно выбрать единый механизм авторизации; предпочтительно Spring
Security с method security, даже если учебная аутентификация заголовками временно
сохраняется. Сервис дополнительно проверяет владение конкретным заказом,
удержанием или уведомлением.

## 8. Предварительный REST-контракт

Контракт уточняется перед соответствующей итерацией.

### Каталог

- `GET /api/v1/movies` — актуальная афиша;
- `GET /api/v1/movies/{movieId}` — карточка фильма;
- `GET /api/v1/movies/{movieId}/screenings` — доступные сеансы;
- `GET /api/v1/screenings/{screeningId}/seats` — схема зала со статусами
  `AVAILABLE`, `HELD` и `BOOKED`.

### Удержание мест

- `POST /api/v1/seat-holds` — атомарно удержать выбранные места текущим клиентом;
- `GET /api/v1/seat-holds/{holdId}` — получить состояние и оставшееся время;
- `DELETE /api/v1/seat-holds/{holdId}` — досрочно освободить своё удержание.

Пример запроса:

```json
{
  "screeningId": 15,
  "seatIds": [71, 72]
}
```

### Заказы

- `POST /api/v1/orders` — подтвердить удержание и оформить заказ;
- `GET /api/v1/orders` — история заказов текущего клиента;
- `GET /api/v1/orders/{orderId}` — детали своего заказа;
- `POST /api/v1/orders/{orderId}/cancel` — отмена, если разрешена правилами.

Пример подтверждения:

```json
{
  "holdId": "0df3a95e-4fe8-4bb3-a18f-744729476f94",
  "products": [
    { "productId": 3, "quantity": 2 }
  ],
  "idempotencyKey": "client-generated-unique-value"
}
```

### Уведомления

- `GET /api/v1/notifications` — история текущего клиента;
- `GET /api/v1/notifications/{id}` — своё уведомление;
- `PATCH /api/v1/notifications/{id}/read` — отметить прочитанным.

Создание уведомления через публичную клиентскую форму следует убрать из
основного интерфейса. Уведомления создаются системой в результате событий.
Административный или лабораторный способ ручной отправки можно сохранить
отдельно, если он нужен для защиты.

### Административный API

- `/api/v1/admin/movies/**` — управление фильмами;
- `/api/v1/admin/auditoriums/**` — управление залами и конфигурацией мест;
- `/api/v1/admin/screenings/**` — создание, изменение и отмена сеансов;
- `/api/v1/admin/products/**` — управление товарами кинобара;
- `/api/v1/admin/notification-categories/**` — управление категориями;
- `POST /api/v1/admin/notifications` — целевая или массовая ручная отправка;
- `/api/v1/admin/settings/booking` — разрешённые параметры политики удержания;
- `/api/v1/admin/laboratory/consistency/**` — эксперимент с Redis-топологией.

Для ручной отправки администратор передаёт аудиторию, категорию, заголовок и
текст. Для системных уведомлений клиентское приложение не вызывает этот метод:
они создаются из событий заказа. Если для уведомления понадобится TTL, он
задаётся административной политикой или типом уведомления, а не произвольным
клиентским параметром.

### Совместимость во время перехода

Существующие `/blocks` и `/locks/execute` не удаляются в начале реформы. Сначала
добавляется новый предметный API и переводится frontend. После этого старые
методы либо остаются только в лабораторном разделе, либо удаляются вместе с их
неиспользуемыми контрактами и mock-реализациями.

## 9. Итерации разработки

### Итерация 0. Зафиксировать исходное состояние и решения

**Статус: завершена 20 октября 2026 года.** Решения зафиксированы в
`docs/DOMAIN_MODEL.md`; противоречия портов исправлены в `AGENTS.md`.

Задачи:

- проверить фактическую структуру backend и frontend перед изменениями;
- согласовать названия сущностей, статусы и правила отмены;
- зафиксировать схему таблиц и ключей Redis;
- согласовать REST-контракт первого вертикального сценария;
- определить миграционный подход для существующих демонстрационных данных;
- устранить противоречия в документации по портам.

Критерий готовности: модель и контракты позволяют однозначно описать успешное
оформление, истечение удержания и конкуренцию двух клиентов за одно место.

### Итерация 1. Каталог, залы, места и сеансы на backend

**Статус: завершена 20 октября 2026 года.** Реализованы JPA-модели каталога,
идемпотентные демонстрационные данные и read-only REST API. До появления билетов
и удержаний все настроенные места имеют статус `AVAILABLE`.

Задачи:

Критерий готовности: через API можно выбрать фильм, конкретный сеанс и получить

### Итерация 2. Архитектурное выравнивание

**Статус: завершена 21 октября 2026 года.** Создание каталожных объектов и
уведомлений вынесено в специализированные фабрики, отображение каталога — в
mapper. Redis-топология читается как конфигурационный список и обслуживается
реестром узлов со стратегией round-robin. Административные операции отделены
маршрутами `/api/v1/admin/**` и проверкой роли до вызова контроллера.

Задачи:

- провести ревизию ручной сборки сущностей и DTO;

- вынести преобразование каталога в `CatalogResponseMapper`;

- заменить отдельные поля `master/replica-1/replica-2` конфигурационным списком
  Redis-узлов;
- реализовать фабрику клиентов, реестр узлов и round-robin стратегию выбора
  реплики;
- разделить probe-операции и изменение топологии между разными сервисами;
- заменить номера реплик в API на типизированные идентификаторы узлов;
- определить матрицу доступа `CLIENT/ADMIN` для всех существующих методов;
- перенести административные и лабораторные мутации под `/api/v1/admin/**`;

- сохранить совместимость текущего учебного входа на время перехода.

Критерий готовности: в сервисах нет жёстко зашитого количества реплик, добавление
узла выполняется конфигурацией, правила создания объектов не размазаны по
инициализаторам и сервисам, а каждый endpoint имеет проверяемую роль.

### Итерация 3. Клиентская афиша и выбор сеанса

схемы зала, общий контракт HTTP/mock, состояния загрузки, пустого результата и
ошибки. Выбранные сеанс и места сохраняются в состоянии оформления до перехода
к серверному удержанию.

### Итерация 4. Временное удержание мест через Redis TTL

  построении схемы зала;
- добавить обратный отсчёт и понятное поведение после истечения удержания.

Критерий готовности: две параллельные попытки удержать пересекающиеся наборы мест

Критерий готовности: подтверждённый заказ появляется один раз, содержит билеты и

### Итерация 6. Системные уведомления

Задачи:

- определить события `SEAT_HOLD_CREATED`, `ORDER_CONFIRMED` и `ORDER_CANCELLED`;
- создавать outbox-событие в той же транзакции, что и изменение заказа;
- доставлять событие в существующий Redis-репозиторий уведомлений с повторными
  попытками и защитой от дублей;
- связать уведомление с заказом через предметные данные;
- добавить отметку о прочтении;
- удалить форму произвольной отправки из обычного клиентского интерфейса.

Уведомление об истечении удержания не должно зависеть от Redis keyspace
notifications: такие события нельзя считать гарантированной очередью. В
интерфейсе истечение отображается по `expiresAt`. Если отдельное уведомление
об истечении станет обязательным, для него нужен надёжный планировщик и
постоянная запись запланированного события.

Критерий готовности: подтверждение заказа приводит к одному уведомлению клиента,
а временная недоступность Redis не теряет событие заказа.

## 10. Проверки, которые сопровождают реализацию

- одно и то же место на разных сеансах доступно независимо;
- купленное место не появляется как свободное после истечения Redis TTL;
- частично пересекающиеся наборы мест удерживаются атомарно;
- чужое удержание нельзя прочитать подробно, освободить или подтвердить;
- истёкшее удержание нельзя подтвердить;
- повторный `idempotencyKey` возвращает результат первого оформления;
- параллельные подтверждения не создают два билета на одно место;
- изменение цены товара не меняет старый заказ;
- cache miss, cache hit и инвалидация категории работают ожидаемо;
- повторная доставка outbox-события не создаёт дубликат уведомления;
- пользователь получает только свои заказы и уведомления;
- клиент получает `403` для административных и лабораторных мутаций;
- администратор может отправить целевое и массовое уведомление;
- добавление новой Redis-реплики не требует изменения Java-кода;
- round-robin стратегия работает с одной, двумя и большим количеством реплик;
- недоступная реплика исключается или приводит к документированному fallback;
- отключённая реплика может вернуть старое экспериментальное значение;
- `WAIT` уменьшает окно рассогласования, но не объявляется полной гарантией
  строгой согласованности или сохранения на диск.

## 11. Границы ближайшей версии

В пользовательский сценарий входят афиша, сеансы, выбор мест, временное
удержание, кинобар, подтверждение заказа, история и уведомления.

До отдельного решения не входят:

- интеграция с настоящей платёжной системой;
- возврат реальных денежных средств;
- динамическое ценообразование;
- несколько филиалов кинотеатра;
- полноценная административная панель управления расписанием;
- электронная почта, SMS и push-доставка;
- production-аутентификация вместо текущей учебной схемы.

Архитектура не должна мешать добавить эти возможности позже. Например, заказ
не следует считать оплаченным только из-за создания HTTP-запроса: учебное
подтверждение явно обозначается в модели и документации.

## 12. Известный архитектурный долг

1. Frontend умеет отмечать уведомления прочитанными и удалять их только в
   mock-режиме, тогда как backend не предоставляет соответствующий контракт.
2. Учебная аутентификация по заголовкам и открытые пароли требуют замены перед
   production-эксплуатацией.
3. Для PostgreSQL настроены постоянный volume и Flyway, но регламент внешнего
   резервного копирования и проверки восстановления ещё не автоматизирован.

Противоречия портов уже устранены: для контейнерного запуска backend доступен на
`16767`, frontend — на `3000`.

3. зафиксировать перечень изменяемых API и моделей;
4. реализовать backend и frontend в пределах выбранной итерации;
5. выполнить проверки, относящиеся к изменённому поведению;
6. обновить документацию по фактически завершённой работе;
7. перечислить оставшиеся ограничения и перейти к следующей итерации только
   после выполнения критерия готовности.

будут строиться на стабильных внутренних контрактах.
